# Telegram-бот «ЛитераторЪ»: план для разработчика

## Текущее состояние и границы

Сайт Next.js 16 + Supabase уже сохраняет брони и RSVP и отправляет уведомления через `src/lib/server/telegram.ts`. Реализованы `/api/booking`, `/api/rsvp`, веб-кабинет, несколько администраторов и атомарная защита вместимости событий. Время заведения — Asia/Bishkek, часы 10:00–22:00. Номер выбранного стола пока хранится в комментарии брони; планировка демонстрационная и не является системой учёта занятости столов.

Webhook, обработчики команд и inline-кнопки пока не реализованы. Этот документ — задание на будущую разработку, не описание работающих команд. Существующую отправку уведомлений нужно сохранить.

Рекомендуется добавить webhook в текущий Next.js проект: `POST /api/telegram/webhook`. Так сайт и бот используют одну базу и общий серверный слой. Бот не должен обращаться к административным API с поддельной браузерной сессией или создавать вторую независимую систему бронирования.

## Этап 1 — webhook, роли и публичные команды

1. Добавить серверный webhook с проверкой `X-Telegram-Bot-Api-Secret-Token`, размера тела и схемы Telegram update через Zod.
2. Подключить безопасную обработку повторных `update_id`: миграция для таблицы обработанных обновлений/очереди, уникальный ID, состояние обработки и восстановление после сбоя. Изменение доменных данных и отметка об обработке должны быть атомарными. При недоступной БД вернуть 5xx, чтобы Telegram повторил доставку.
3. Для MVP читать `TELEGRAM_ADMIN_USER_IDS` и разрешённый `TELEGRAM_CHAT_ID` из env. Проверять одновременно `from.id` и chat_id; приватные функции доступны только в разрешённых приватных чатах. Username не является идентификатором доступа. При пустой конфигурации запретить административные команды.
4. Позже заменить ручной список привязкой Telegram user_id к учётной записи Supabase через одноразовый короткоживущий код из веб-кабинета. Отзыв доступа сотрудника должен отключать его команды бота. Не выдавать права только потому, что человек знает ссылку на бота.
5. Добавить публичные команды:

| Команда | Поведение |
| --- | --- |
| `/start` | RU/EN и кнопки «Сайт», «Меню», «Столы», «Афиша», «Контакты» |
| `/help` | Доступные команды и пояснение о подтверждении брони администратором |
| `/menu` | Ссылка на актуальное меню сайта |
| `/tables` | Ссылка на текущую схему зала и выбор стола |
| `/book` | Ссылка на «Литературный резерв» |
| `/events` | Ближайшие опубликованные события, свободные места, ссылки на запись |
| `/contacts` | Телефон, WhatsApp, часы; вымышленный адрес явно обозначен |
| `/language` | Переключение RU/EN |

Для публичных ответов расширить Telegram helper отправкой в явно переданный chat_id. Источник chat_id — только проверенный update; личные данные гостей в публичных ответах запрещены. Ограничить частоту команд. Зарегистрировать webhook и меню команд после деплоя; не сбрасывать накопленные обновления без отдельного решения.

## Этап 2 — управление бронями: первый полезный MVP

| Команда администратора | Поведение |
| --- | --- |
| `/today` | Брони на сегодня по Бишкеку, группировка по статусу |
| `/pending` | Ожидающие заявки с пагинацией |
| `/booking <id>` | Одна заявка: имя, телефон, дата/время, гости, пожелание по столу и комментарий |
| `/confirm <id>` | pending → confirmed |
| `/decline <id>` | pending → declined; явное подтверждение действия, причина — отдельный последующий шаг |
| `/admin` | Ссылка на защищённый веб-кабинет |

В новой заявке нужны inline-кнопки «Подтвердить», «Отклонить», «Открыть кабинет». В callback_data передавать только тип действия и UUID, не телефоны; лимит Telegram — 64 байта. Проверять права заново на каждом callback, включая автора нажатия.

Вынести изменение статуса в общий серверный сервис для webhook и `/api/admin/bookings`. Переход выполнять условным UPDATE с ожидаемым статусом pending. Два администратора или повторный callback не должны дважды менять статус: второй видит уже принятое решение и автора. Добавить журнал действий (actor, before/after, timestamp) миграцией; не подделывать текущую историю старых записей.

Всегда вызывать answerCallbackQuery, обновлять сообщение и убирать недоступные кнопки. Отказ гостя/ошибочный ID/удалённая запись должны давать понятный ответ без сырых ошибок БД. Подтверждение предпочтения по столу остаётся ручным: бот не может показывать «стол свободен» без полноценной модели столов, времени начала/окончания и атомарного контроля пересечений.

## Этап 3 — события и RSVP

- `/event <id>` — событие, вместимость, занятые/свободные места и ссылка на кабинет.
- `/rsvps <event_id>` — участники с пагинацией; только авторизованным администраторам в приватном чате.
- В уведомлении RSVP — «Открыть событие», «Список участников», при необходимости «Отменить запись» с отдельным подтверждением. Отмена должна освобождать места тем же способом, что и веб-кабинет.
- Сейчас RSVP получает место сразу через атомарную RPC. У event_rsvps нет статусов pending/confirmed/declined. Нельзя просто переиспользовать команды подтверждения брони для RSVP.
- Если потребуется модерация RSVP, сначала спроектировать отдельную миграцию статусов и обновить RPC, агрегат мест, уникальность по телефону и тесты конкуренции. Явно определить, занимают ли ожидающие заявки места. Не вставлять RSVP напрямую в обход `create_event_rsvp`.

## Этап 4 — надёжная доставка и уведомления гостям

1. Добавить outbox/очередь и повторную доставку уведомлений. Сохранённая бронь не должна теряться из-за недоступности Telegram. Повторная попытка не создаёт новую бронь или RSVP.
2. Создание заявки и запись задачи уведомления — одна транзакция через проверенную серверную RPC; worker доставляет и фиксирует результат. Состояние доставки, ошибки и число повторов доступны владельцу без токенов и лишних персональных данных.
3. Ввести явную привязку гостя: одноразовая ссылка `t.me/...?...start=<opaque-token>`, срок действия, защита от повторного использования и подтверждение согласия. Телефон или username не позволяют отправить гостю Telegram-сообщение автоматически.
4. Только после привязки — уведомления об одобрении/отказе и напоминания. Отмена гостем требует проверки владения конкретной заявкой; команды `/mybookings`, `/cancel` не принимают произвольный ID без авторизации.
5. Дайджест администратору на день, напоминания, `/stats` и расширенная работа со столами — отдельные следующие задачи. Для столов сначала нужны постоянные table_id и интервалы брони в БД, правила длительности, закрытия и защиты от пересечений.

## Переменные, миграции и эксплуатация

Уже есть `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, Supabase URL/service-role. Новые требования: `TELEGRAM_WEBHOOK_SECRET`, для MVP `TELEGRAM_ADMIN_USER_IDS`. Реальные значения вводятся в секреты окружения/Vercel, в README только placeholders. Service-role и webhook secret не попадают в клиентские bundles, сообщения или логи.

Все изменения БД — отдельные timestamped миграции, обновлённый schema.sql, RLS и запрет прямого браузерного доступа к bot_updates/audit/outbox/привязкам. Для разработки предпочтителен отдельный тестовый бот: один токен имеет один webhook, параллельные разработчики иначе перезаписывают настройки друг друга. Проверять getWebhookInfo после регистрации. Персональные данные не рассылать в общий чат; маскировать их в технических логах.

## Приёмка MVP

- Публичный пользователь видит только публичные команды и не получает чужие брони/телефоны.
- Неверный webhook secret отклоняется. Знание callback_data или подмена username не дают доступ.
- `/today` корректен при смене даты в Бишкеке; `/pending` имеет пагинацию.
- Подтверждение/отклонение видно и в боте, и в веб-кабинете. Два одновременных решения и повторная доставка не создают повторных действий.
- Удалённая запись, запрещённый actor, истёкшая привязка и сбой Telegram/БД обрабатываются предсказуемо; приватные данные не утекают.
- RSVP остаётся атомарным: два запроса на последнее место не могут оба пройти; отмена освобождает нужное количество мест.
- Unit-тесты команд/прав/схем и интеграционные тесты webhook, идемпотентности и статусов. Build/lint и существующие проверки сайта проходят.

Порядок PR: (1) webhook + роли + публичные команды; (2) брони и inline-кнопки; (3) RSVP; (4) outbox и opt-in гостя. Рекомендуемый первый релиз — первые два PR, затем расширение по реальной работе команды.
