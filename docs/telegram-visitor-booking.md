# Меню и бронирование в Telegram, доступность столов

Команды `/menu`, `/tables`, `/book` (также `/book_a_table`), `/events`, `/contacts` работают внутри чата. Главное меню использует callback-кнопки. Меню читает те же `menu_items`, что сайт: категории, названия, состав, порция, крепость, цена. Афиша выводит ближайшие опубликованные события с описанием и числом мест, с переходом к следующим событиям. Контакты содержат адрес, телефон, часы работы, WhatsApp и карту.

Бронирование: дата → время → гости → свободный стол → имя → кыргызстанский телефон → проверка → отправка. До отправки запись не создаётся. `/cancel` отменяет диалог; кнопка «Назад» возвращает к выбору даты. Сессия действует 20 минут; устаревшие кнопки не меняют текущий выбор. Подтверждение гостем, создание заявки `pending`, dedup update и ответы гостю/владельцу сохраняются одной транзакцией. Администратор принимает решение существующими командами или в кабинете.

На страницах столов и бронирования используется общий календарь RU/EN, быстрый выбор сегодня/завтра, интервалы прибытия по 30 минут, счётчик гостей и итог визита. Выбор переносится между страницами в памяти, дата/время/гости также сохраняются в ссылке бронирования. Контактные данные в URL и localStorage не попадают.

Правила занятости:

- Время заведения — Asia/Bishkek, 10:00–22:00. Визит длится 2 часа, но заканчивается не позже 22:00. Последний слот интерфейса — 21:30.
- `pending` и `confirmed` удерживают конкретный `table_id`; отклонение освобождает его. Заявки без выбора стола остаются запросом на ручную рассадку и не занимают произвольный стол.
- `GET /api/tables?date=YYYY-MM-DD&time=HH:mm&guests=N` возвращает только массив ID свободных подходящих столов, без данных гостей, с `Cache-Control: no-store`.
- PostgreSQL trigger сериализует записи по столу через транзакционную advisory-блокировку и запрещает пересечения при создании и изменении заявки, включая восстановление отклонённой. Конфликт сайта возвращает HTTP 409; бот предлагает начать новый выбор.
- Старые заявки с прежним серверным префиксом номера стола в комментарии получают `table_id`. Уже существовавшие пересечения не отменяются автоматически: они закрывают соответствующие интервалы до решения администратора.
- Черновик Telegram хранится в закрытой `telegram_sessions.flow`, очищается после истечения сессии при следующем update. Браузерным ролям закрыты таблицы бота и RPC доступности.

## Включение на работающем сайте

1. В существующем проекте Supabase применить `supabase/migrations/20261108000100_0007_table_availability.sql` после миграций 0001–0006. Это нужно сделать **до деплоя кода**. Миграция допускает повторное применение.
2. Развернуть эту ветку на существующем Vercel-проекте. Новые переменные окружения не нужны: используются прежние ключи Supabase, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` и домен сайта.
3. При уже настроенном webhook повторный запуск setup и ротация секрета не требуются. Новые кнопки появятся после `/start` или `/help`; старые отправленные URL-кнопки Telegram не меняет задним числом.
4. Проверить в действующем боте меню, события, контакты и заявку на будущий интервал; убедиться, что тот же стол недоступен на сайте, а после отклонения снова появляется. Такой тест создаёт настоящую заявку и уведомление владельцу.

## Проверки этой реализации

Vitest проверяет диалог, меню, валидацию телефона, устаревшие/просроченные кнопки, лимиты callback, API доступности и HTTP 409. PGlite проверяет повторное применение миграции, перенос старого номера стола, интервалы/соседние визиты, освобождение и восстановление, вместимость, закрытие, права, атомарность брони с outbox и отсутствие повторной записи при replay. Production build и TypeScript проверяются стандартной сборкой.

Визуальная проверка выполнена локально на узком и широком экранах. Подключение к настоящему Supabase, отправка в Telegram и production-деплой в этой сессии не проверены: серверные ключи в рабочей копии отсутствуют. PGlite проверяет PostgreSQL-логику, но не заменяет испытание конкурентных подключений к production PostgreSQL.
